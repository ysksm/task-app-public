2026-11-01 · 提案（未決定）

01 · きっかけ

マイタスクの使い方が、作った本人にもわからなくなってきた

起きていること

ティア・保存ビュー・リスト/ツリー・ボード・マップ・QA受信箱…と機能が増えるたびに、
「どれをいつ使うのか」の分担があいまいになっている

原因

要求仕様（docs/01-requirements.md）は 「何ができるか」で整理されている。
「誰が・どんな場面で・何のために」が書かれていないので、機能の置き場所と役割を判断する軸がない

やりたいこと

アプリを作るときにユースケースを考え、それを満たしていく進め方を開発に組み込みたい。
さらに、それを支える仕組みをアプリ自身に持たせたい
この資料の提案：タスクを管理するアプリから一段上がり、要求から実装・検証までを 1 本の糸でつなぎ、開発サイクルを回すアプリにする

02 · 世の中の手法

要求を扱う手法は、それぞれ別の問いに答えている

手法何を決めるか特徴このアプリとの相性
ペルソナ誰が使うか利用者像を 2〜3 人つくり、迷ったら「この人なら使うか？」で判断する◎ 利用者は実在（本人と AI エージェント）。架空にせず実在の役割で書ける
ジョブ理論（JTBD）なぜ使うか「〇〇な状況で、〇〇したい。そうすれば〇〇できる」。機能ではなく状況から考える◎ 「朝、今日やることを決めたい」のような場面が書ける
ユースケース（Cockburn）目的までの手順基本の流れと例外の流れを手順として書く○ 厳密だが重い。API 仕様と相性がよい
ストーリーマッピング（Patton）使う流れ全体と、どこまで作るか横に利用の流れ（活動 → 手順）、その下にストーリー。横線でリリース単位に切る◎ 「使い方」の全体像そのもの。今回の悩みに一番効く
インパクトマッピング機能は本当に必要かゴール → 誰が → 行動がどう変わるか → 機能、の木○ 機能を減らす判断に使える
BDD / 例示マッピング完成の条件受け入れ条件を Given/When/Then で書き、テストにつなげる◎ 既存の e2e・apitest にそのままつながる
トレーサビリティ要求とテストの対応要求 ID → 画面 → テストの対応表○ 要求 ID はすでにある。拡張するだけ

03 · 中心となる考え方

要求は「生き続ける仕様」、タスクは「使い切るもの」

要求（L0〜L6）

ペルソナ・ジョブ・活動・手順・ストーリー・受け入れ条件。
完了で閉じない。版を重ねて育つ。
「この機能は何のためにあるか」をアプリの中に残す役目

タスク（L8）

要求を満たすために一時的に発生し、終われば閉じる。
人か AI エージェントが担当する。
今のタスクアプリが扱っているのはこちらだけ
今のアプリが使いにくくなったのは「使い切る側」しか持っていないから。
要求の側を足し、両者をつなぐことで、機能の存在理由と完成度が見えるようにする

07 · 開発サイクル

6 つの段階を回し、学びを次の発見に戻す

① 発見

ペルソナ・ジョブ・フィードバックを整理

② 定義

ストーリーマップに手順とストーリーを置く

③ 分解

受け入れ条件 → 設計要素 → タスク

④ 作る

AI エージェント中心に実装

⑤ 確かめる

CI の結果を取り込み、人が受け入れ確認

⑥ 学ぶ

使った気づきをフィードバックに

⑥ から ① へ

段階ごとに関門を置く

次へ進む条件をシステムが自動で判定する（次のページ）。人が毎回チェックリストを見なくてよい

どこが抜けているかが常に見える

着手可能でないストーリー、テストのない条件、つながっていない機能が一覧になる

08 · 関門

次へ進む条件を、つながりの有無から自動で判定する

段階やること次へ進む条件
① 発見ペルソナ・ジョブ・フィードバックを整理するジョブが 1 つ以上の活動に結びついている
② 定義ストーリーマップに手順とストーリーを置く着手可能：手順につながっている／受け入れ条件が 1 つ以上／設計要素が特定済み
③ 分解受け入れ条件 → 設計要素 → 開発タスクに落とすすべての受け入れ条件に担当タスクと予定テストがある
④ 作る実装する（AI エージェント中心。チェックポイントと質問は既存の仕組み）タスクがすべて完了
⑤ 確かめるCI のテスト結果を取り込み、人が受け入れ確認完了：全条件のテストが成功し、ガイドも更新済み
⑥ 学ぶ使ってみての気づきをフィードバックとして登録影響するストーリーが特定され、① に戻る

09 · 自動でできるようにしたいこと

つながっているから、状態の集計と書類づくりは機械に任せられる

カバレッジ付きストーリーマップ

緑＝検証済み、黄＝実装中、灰＝未定義、赤＝テスト失敗。マップを見るだけで完成度がわかる

孤立チェック

どの手順にもつながらない機能・画面・テストを一覧に。「何のための機能か」を検出する

使い方ガイドの自動生成

活動を章、手順を節として書き出す。docs/06-guide.md を置き換える

トレース表とスライドの生成

要求 → 設計 → テストの対応表と設計スライド。今の手作業の docs/ を置き換える

テストとの結びつけ

テスト名にタグ（例 @AC-142）。CI の Playwright / vitest のレポートを取り込み、条件ごとに成否を反映

コードとの結びつけ

コミットや PR の本文に ID を書くと自動で紐づく

10 · AI エージェントの役割

下書きは AI、決めるのは人

作業AI人
ストーリーから受け入れ条件を下書きする○ 下書き承認する
受け入れ条件から設計要素とタスクに分解する○ 下書き承認する
実装とテストを書く○ 実施必要に応じて質問に答える
フィードバックから影響するストーリーを推定する○ 推定優先度を決める
ゴール・ペルソナ・リリースの線引き提案のみ決める
AI は MCP で上の階層まで読めるので、「なぜこれを作るのか」を知ったうえで作業できる。
判断の質が上がり、質問やチェックポイントも要求 ID に結びつく

11 · 画面構成のイメージ

ストーリーマップを中心に、上下の階層へ移る

① プロダクトのホーム

ゴールと指標、サイクルの現在地、関門で止まっている項目

② ペルソナとジョブ

誰が、どんな状況で何をしたいか

③ ストーリーマップ

メイン画面。横に活動と手順、縦にリリース。カバレッジの色付き

④ ストーリー詳細

ペルソナから手順・条件・設計・タスク・テストまでを 1 画面で縦に見せる

⑤ 健全性

孤立・抜け・失敗テストの一覧

⑥ フィードバック受信箱

使って気づいたことを登録し、ストーリーに振り分ける

⑦ 課題・ボード・QA受信箱

既存。L8 の開発タスクを扱う場所としてそのまま使う

12 · 作り方

今のタスクアプリを土台に、要求の層を上に足す

そのまま使うもの

課題・MCP・質問・チェックポイント・受け入れ依頼。
L8（開発タスク）と L9（検証）の受け皿になる

新しく足すもの

要求（L0〜L6）と設計要素（L7）は課題タイプとしてではなく別のテーブルで持つ。
完了で閉じない・版を重ねる、というライフサイクルが課題と違うため

今までどおり

API を先に定義し、apitest で振る舞いを固定する。
将来の Rust への書き直しでも同じテストが使える
別アプリにしない理由：開発タスク・AI エージェント接続・質問の仕組みをゼロから作り直すことになり、
しかも要求と開発タスクのつなぎ目が 2 つのアプリにまたがってしまう

13 · 段階的な進め方

まずこのアプリ自身の要求で試す

段階内容試す対象
M1要求モデル（L0〜L6）、ストーリーマップ表示、ストーリーとタスクの紐付けこのアプリ自身（TAPP）の要求を登録する。まずマイタスク周り
M2受け入れ条件とテストタグの紐付け、CI 結果の取り込み、カバレッジ色既存の e2e と apitest にタグを付ける
M3関門の自動判定、AI による分解の下書き、ガイドとスライドの生成docs/ の手作業を置き換えられるか確かめる
M4フィードバックの循環、指標日々使った気づきを登録して次のサイクルを回す

M1 の前に、アプリを変えずに「今の機能をストーリーマップに貼る棚卸し」を文書で行うと、
使い方がわかりにくくなった原因（孤立・重複した機能）が先に見える
