05 · 棚卸し: マイタスク（S01）

手を入れたいのは 7 つ。残りはそのまま手順に対応する

機能手順判定理由
タブ「担当」A1-1, A2-1残すマイタスクの本体
タブ「起票したもの」A3-3 ？見直す自分で持つものも混ざる。「任せたもの」（起票 = 自分・担当 = エージェント）に
タブ「回答待ち QA」A4-1まとめるQA インボックスの「未回答 ＋ 自分宛て」と同じ。答えるのは S02 が向く
表示「ツリー」？手順が要る横断のツリーはどの手順でもない。使わないなら外す
グループ「担当者」・担当者フィルタなし外す担当タブでは常に自分。選んでも意味のある結果にならない
並び「手動」なし外す手動の順番は同じ親の中の並び。横断の一覧では意味がない
「完了を隠す」A1-1既定を変える画面は既定オフ、MCP は未完了だけが既定。朝の用途ならオンに
「配下」フィルタなし残す（低）ツリーと同じく、手順が決まらなければ外してよい
新規・注力のみ・並び（期日/優先度）・ティア/種別/優先度フィルタ・ビュー保存・サイドピークA1〜A3残す手順にそのまま対応する

07 · わかりにくさの原因と、整理の案

原因は 5 つ。M1 とは別の小さな変更で片づく

見えてきたこと

1
同じものが 2 か所
「回答待ち QA」タブと QA インボックス
2
朝の画面が決まっていない
マイタスクと「全体ボード ＋ 注力のみ」
3
意味のない選択肢
担当タブのグループ「担当者」・担当者フィルタ、横断の「並び: 手動」
4
既定のずれ
画面は完了も出し、MCP は未完了だけ
5
目的のわからないもの
「起票したもの」タブ、マイタスクのツリー表示

整理の案

T1
「回答待ち QA」タブを外し、QA インボックスに一本化
← 1
T2
朝 = マイタスク、振り返り = 全体ボードと決めてガイドに書く。「完了を隠す」を既定オンに
← 2, 4
T3
担当タブでグループ「担当者」と担当者フィルタを出さない。マイタスクで「並び: 手動」を出さない
← 3
T4
「起票したもの」を「任せたもの」（起票 = 自分・担当 = エージェント）に
← 5
T5
マイタスクのツリー表示は、手順が決まらなければ外す
← 5

08 · M1 の範囲

要求の層（L1〜L6）とつながりだけを入れる

入れる入れない（後の段階）
ペルソナ・ジョブ・活動・手順・ストーリー・受け入れ条件（L1〜L6）ゴール・指標（L0）。M1 はプロジェクトの説明で代用
ストーリーと手順、ストーリーとイシューのつながり設計要素（L7）、テストとの結びつけ・CI の取り込み（M2）

エージェントは作業の理由を読める

09 · 決めたいこと: 今の「受入基準」との関係

要求は新しいテーブルに持ち、イシューから「つなぐ」（案 A）

案 A（おすすめ）新しいテーブル

ストーリー（L5）と受け入れ条件（L6）は新しいテーブル。イシューはストーリーにつながる。
イシューの受入基準は「その回の実装で確かめること」として今のまま。

長所：イシューが Done になっても要求は残る。受入検査を壊さない
短所：「受け入れ条件」と「受入基準」の 2 つの言葉。画面で区別が要る

案 B 今の仕組みを使う

ストーリー = 今の「ストーリー」種別のイシュー、受け入れ条件 = 今の受入基準に Given/When/Then を足す。

長所：追加が少ない
短所：ストーリーのイシューが Done で閉じると、要求も閉じたことになる。「要求は生き続ける」と合わない

案 A では、イシューの受入基準を作るときに「つながっているストーリーの受け入れ条件から写す」ボタンを付ける（写すだけで、同期はしない）

10 · データモデル（マイグレーション 009）

種類ごとに連番のキー。消さずにアーカイブ、変更は履歴に残す

種類キーの例テーブル
ペルソナTAPP-P1req_personas
ジョブTAPP-J3req_jobs
活動TAPP-A1req_activities
手順TAPP-A1-2req_steps
ストーリーTAPP-ST12req_stories
受け入れ条件TAPP-AC42req_criteria

つながり：req_job_activities（ジョブ ⇄ 活動）、req_story_steps（ストーリー ⇄ 手順）、req_story_issues（ストーリー ⇄ イシュー）。どれも N:N

キーの採番：req_counters（プロジェクト × 種類）。アーカイブしてもキーは使い回さない

版：M1 は req_changes（誰が・いつ・何を）で代用。リリース時点の固定は M3 で検討

リリース：ストーリーの release（自由な文字列、例 R1）。マップの横線はこの値でまとめる

受け入れ条件：given / when / then の 3 つの欄。M2 でテストのタグ（@TAPP-AC42）につなぐ

11 · API と MCP

マップ全体を 1 回で取り、各要素は個別に編集する

メソッドとパス（/api/v1/projects/{key}/…）内容
GET storymapマップ全体（ペルソナ・ジョブ・活動・手順・ストーリー・条件の数・イシューの進捗）と抜け（gaps）
GET/POST personas · jobs、PATCH/DELETE …/{キー}ペルソナ・ジョブ（ジョブは活動とのつながりも）
POST activities、POST activities/{キー}/steps、PATCH/DELETE活動と手順。並べ替えは position
GET/POST stories、GET/PATCH/DELETE stories/{キー}ストーリー（手順とのつながり・リリースも）
POST stories/{キー}/criteria、PATCH/DELETE criteria/{キー}受け入れ条件
PUT/DELETE stories/{キー}/issues/{イシューキー}ストーリーとイシューをつなぐ・外す
GET /api/v1/issues/{キー}（既存）stories（キー・タイトル・条件）を足す

gaps（抜け）

手順につながらないストーリー、ストーリーのない手順、条件のないストーリー、イシューのないストーリー、活動につながらないジョブ

MCP

get_issue に stories を足す（B2-2）。読み取りの get_storymap を足す。書き込みのツールは M3（AI の下書き）で
