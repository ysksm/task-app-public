02 · 世の中の手法

要求を扱う手法は、それぞれ別の問いに答えている

手法何を決めるか特徴このアプリとの相性
ペルソナ誰が使うか利用者像を 2〜3 人つくり、迷ったら「この人なら使うか？」で判断する◎ 利用者は実在（本人と AI エージェント）。架空にせず実在の役割で書ける
ジョブ理論（JTBD）なぜ使うか「〇〇な状況で、〇〇したい。そうすれば〇〇できる」。機能ではなく状況から考える◎ 「朝、今日やることを決めたい」のような場面が書ける
ユースケース（Cockburn）目的までの手順基本の流れと例外の流れを手順として書く○ 厳密だが重い。API 仕様と相性がよい
ストーリーマッピング（Patton）使う流れ全体と、どこまで作るか横に利用の流れ（活動 → 手順）、その下にストーリー。横線でリリース単位に切る◎ 「使い方」の全体像そのもの。今回の悩みに一番効く
インパクトマッピング機能は本当に必要かゴール → 誰が → 行動がどう変わるか → 機能、の木○ 機能を減らす判断に使える
BDD / 例示マッピング完成の条件受け入れ条件を Given/When/Then で書き、テストにつなげる◎ 既存の e2e・apitest にそのままつながる
トレーサビリティ要求とテストの対応要求 ID → 画面 → テストの対応表○ 要求 ID はすでにある。拡張するだけ
