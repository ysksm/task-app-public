01 · 背景と課題

エージェントの作業が「見えない・届かない・つながらない」

見えない

何をどこまで進めたか、なぜその判断をしたかが後から追えない

届かない

判断に迷った点が人間に届かず、勝手に決めるか止まってしまう

つながらない

エピック・ストーリー・QA・受入検査が、エージェントの作業単位と分断している

人間のプロジェクト管理とエージェントの作業記録を、1つの階層データで管理する

2 / 18

課題の3点。解決の方針は、人間とエージェントが同じ階層データを見て、同じチケットに記録すること。

02 · コンセプト

内部は Linear ライク、外部は Jira 互換と MCP

Linear ライク UI

シンプルなステータスと階層データ。キーボード中心で速く操作できる

人間: PM・QA・受入検査

Jira 互換 API (v3)

REST API v3 互換。ORCA の Jira 連携（Cloud モード）からそのまま接続できる

ORCA: タスク取得・更新

MCP サーバー

エージェントがチェックポイント記録や QA 起票をツールとして呼べる

エージェント: 記録・質問

手元の PC で動く単一バイナリ（ほかの端末からも接続可）。UI・API・MCP は同じサービス層を通る

3 / 18

ORCA は stablyai/orca。Jira の Cloud モードでは /rest/api/3 を Basic（メール + API トークン）で呼び、説明・コメントは ADF でやり取りすることをソースで確認済み。接続先 URL は atlassian.net に限定されない。

03 · 利用者

人間・エージェント・ORCA の3者が同じチケットを扱う

アクター主な操作
👤 プロジェクト管理者エピック・ストーリー定義、優先度付け、マインドマップで全体確認
👤 開発者 / QA 回答者エージェントの質問に回答、作業レビュー、自分の担当確認
👤 受入検査者受入基準のチェック、合格 / 差し戻しの判定
🤖 AI エージェントタスク取得、ステータス更新、チェックポイント記録、QA 起票、子タスク作成
🔗 ORCAJira クライアントとして検索・閲覧・作成・遷移・コメント

サーバーは手元の PC で 1 つ。人間は主にオーナー1名（ほかの端末からはパスワードでログイン）。データ上は複数の人間とエージェントを区別する

09 · 受入検査

受入基準ごとに判定し、合格か差し戻しを決める

STEP 1

基準を定義

ストーリー / フィーチャーに受入基準をチェックリストで書く

STEP 2

受入待ちへ

ステータスを「受入待ち」にすると受入検査画面に並ぶ

STEP 3

判定

基準ごとに OK / NG とコメント。合格で Done、差し戻しで In Progress

判定時、未完了の子チケットや未回答 QA があれば警告。判定の履歴（回数・判定者・理由）はすべて残す

11 · Jira 互換 API（ORCA 連携）

ORCA が呼ぶ REST API v3 を実装する

メソッドパス（/rest/api/3 以下）
GET/myself · /serverInfo · /project/search
GET POST/search/jql（JQL）
GET POST PUT/issue · /issue/{key}
PUT/issue/{key}/assignee
GET POST/issue/{key}/transitions
GET POST/issue/{key}/comment
GET/issue/createmeta/… · /priority · /user/search
GET/rest/agile/1.0/board（+ configuration）

認証

Basic（メール + API トークン）。説明・コメントは ADF ⇔ Markdown 変換

JQL サブセット

project, key, issuetype, status, assignee, parent, text ~ など。AND / OR / NOT、currentUser()、ORDER BY

種別の対応

Epic / Story / Feature / Task / Question。親子は fields.parent

12 / 18

エンドポイントは stablyai/orca の src/main/jira（Cloud モード）を調べて洗い出した。ORCA の既定 JQL 例: assignee = currentUser() AND resolution = Unresolved ORDER BY updated DESC。v2（Server/DC）は今回スコープ外。

13 · 複数端末からの利用（§4.12）

スマホや別の PC からも、ログインして使う

ID要求
MD-01--host で外部から接続できるアドレスで待ち受けられる。既定は 127.0.0.1 のまま
MD-02ログイン画面。人間はユーザー名 + パスワード、エージェントはトークンだけ
MD-03パスワードは設定画面と taskapp passwd で設定。8 文字以上、ハッシュで保存し API・エクスポートに出さない
MD-04ログインはサーバーが動いている間だけ有効。ログアウトできる
MD-05パスワードなしの自動ログインは、この PC（接続元と Host がループバック）からだけ
MD-06外部向けで起動したら、暗号化されないことを警告。保護は VPN（Tailscale など）に任せる
MD-07MCP（HTTP）と Jira 互換 API はほかの端末からもトークンで。設定画面に URL を出す
MD-08（S）パスワードの総当たりを遅らせる（続けて失敗したら一時的に断る）
MD-09（S）同じマシンのリバースプロキシ（tailscale serve など）の後ろで動かせる。MCP はプロキシの Host を受け、自動ログインは止める

13 · 要求の層（ストーリーマップ・§4.13）

誰が・どんな場面で・何のために、をイシューとつなぐ

ペルソナとジョブ（REQ-01）

人 / AI のペルソナ。ジョブは「状況・したいこと・そうすれば」で書き、活動につなぐ

ストーリーマップ（REQ-02, 05）

活動と手順を横、リリースを縦。手順の下にストーリー。手順のないストーリーなどの抜けを一覧

受け入れ条件とイシュー（REQ-03, 04, 08）

Given / When / Then。同じプロジェクトのイシューをつなぎ、カードの色はその状態から。受入基準へ写せる

閉じない・使い回さない（REQ-06, 07）

削除はアーカイブ、キー（TAPP-ST12 など）は使い回さない。変更履歴。イシュー詳細と MCP に「なぜ」

14 · 要求の層をゆるく使う（案 D・§4.13）

ひとことで書き始め、分類は後から AI と付ける

ひとこと入力と未整理（REQ-09）

タイトルだけで作れる。ペルソナ・手順・リリースは選ばず、最初の列「未整理」へ

本文と 1 行の条件（REQ-10, 11）

自由な本文（Markdown）。条件は結果の 1 行で書け、前提・操作は「詳しく」

使うときだけ（REQ-12）

ペルソナ・活動が 0 件なら、絞り込みも列も出さない。抜けは警告にせず数だけ

AI が聞いてから直す（REQ-13）

MCP の create_story・update_story。動かす前に ask_question で聞き、はいだけ直す
