# 08 開発サイクル: マイタスクの棚卸しと M1 設計

[提案スライド「アプリ開発アプリ構想」](slides/devcycle.html) の続き。オーナーの決定（2026-11-02）:

- 今のタスクアプリを**拡張**して検証する（別アプリにしない）
- 利用者は**オーナー本人と AI エージェントだけ**

この文書は、(1) マイタスク周りの今の機能をストーリーマップに貼った**棚卸し**と、(2) 要求の層を足す **M1 の設計**。2026-11-02、M1 を案 A で実装した（確認ポイント [extra-10](checkpoints/extra-10.md)、変更点のスライド [M1 実装: UI と DB の変更点](slides/m1.html)）。棚卸しの整理 T1〜T5 はまだ。M1 は固すぎるという感想を受けて、構造をゆるくする案を [09](09-requirements-loose.md) にまとめた。

### 4.4 見えてきたこと

「使い方がわからなくなった」の原因は、次の 5 つ。

1. **同じものが 2 か所にある**: 「回答待ち QA」タブと QA インボックス。
2. **朝の画面が決まっていない**: マイタスクと「全体ボード ＋ 注力のみ」のどちらでも朝の用途を満たせる。
3. **意味のない選択肢がある**: 担当タブの「グループ: 担当者」「担当者」フィルタ、横断の「並び: 手動」。
4. **既定がずれている**: 画面は完了も出し、エージェント（MCP）は未完了だけを出す。
5. **目的のわからないものがある**: 「起票したもの」タブ、マイタスクのツリー表示。

### 4.5 整理の案（M1 とは別の小さな変更）

| # | 変更 | 対応する見えてきたこと |
|---|---|---|
| T1 | マイタスクから「回答待ち QA」タブを外す。サイドバーの QA インボックスのバッジに一本化 | 1 |
| T2 | 朝 = マイタスク、振り返り = 全体ボード、と決めてガイドに書く。マイタスクは「完了を隠す」を既定でオンに | 2, 4 |
| T3 | 担当タブでは「グループ: 担当者」と担当者フィルタを出さない。マイタスクでは「並び: 手動」を出さない | 3 |
| T4 | 「起票したもの」を「任せたもの」（自分が起票し、エージェントが担当）に変える | 5 |
| T5 | マイタスクのツリー表示は、手順が決まらなければ外す | 5 |

### 5.1 範囲

### 5.2 既存の「受入基準」との関係（決めたいこと）

今のアプリには、ストーリー/フィーチャーのイシューに付く**受入基準**（`acceptance_criteria`、受入検査で OK/NG を付ける）がすでにある。L5 ストーリー・L6 受け入れ条件との関係は 2 通り考えられる。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A（おすすめ）** | L5・L6 は**新しいテーブル**。イシューは L5 に**つながる**。イシューの受入基準は「その回の実装で確かめること」として今のまま | 要求は完了で閉じない（イシューは Done になっても要求は残る）。既存の受入検査を壊さない | 似た言葉が 2 つ（受け入れ条件と受入基準）。画面で区別が要る |
| B | L5 = 今の「ストーリー」種別のイシュー、L6 = 今の受入基準に Given/When/Then を足す | 追加が少ない | ストーリーのイシューが Done で閉じると要求も閉じたことになる。提案の「要求は生き続ける」と合わない |

A の場合、イシューの受入基準を作るときに「つながっているストーリーの受け入れ条件から写す」ボタンを付ける（M1 では写すだけ。同期はしない）。

### 5.3 データモデル（マイグレーション 009）

すべてプロジェクトに属する。表示用のキーはプロジェクトの中で種類ごとの連番。

| 種類 | キーの例 | テーブル |
|---|---|---|
| ペルソナ | `TAPP-P1` | `req_personas` |
| ジョブ | `TAPP-J3` | `req_jobs` |
| 活動 | `TAPP-A1` | `req_activities` |
| 手順 | `TAPP-A1-2` | `req_steps`（活動の中の連番） |
| ストーリー | `TAPP-ST12` | `req_stories` |
| 受け入れ条件 | `TAPP-AC42` | `req_criteria` |

```
req_personas   (id, project_id, num, name, kind human|agent, description, position, created_at, updated_at, archived_at)
req_jobs       (id, project_id, num, persona_id, situation, motivation, outcome, position, …)
req_activities (id, project_id, num, persona_id, name, description, position, …)
req_steps      (id, activity_id, num, name, description, position, …)
req_job_activities (job_id, activity_id)                 -- N:N
req_stories    (id, project_id, num, title, persona_id, i_want, so_that, release, position, …)
req_story_steps    (story_id, step_id)                    -- N:N
req_criteria   (id, story_id, num, given, when_text, then_text, position, …, archived_at)
req_story_issues   (story_id, issue_id)                   -- N:N。開発タスク（既存のイシュー）
req_counters   (project_id, kind, next)                   -- キーの連番
req_changes    (id, entity, entity_id, actor_id, field, old, new, at)   -- 変更履歴（版の代わり）
```

- 削除は `archived_at`（論理削除）。キーは使い回さない。
- 「版を重ねる」は M1 では変更履歴で代用（誰が・いつ・何を）。版の固定（リリース時のスナップショット）は M3 で検討。
- `release` は M1 では自由な文字列（例 `R1`）。リリースの横線はこの値でまとめる。

### 5.4 API（`/api/v1`、OpenAPI に追加）

| メソッドとパス | 内容 |
|---|---|
| `GET /projects/{key}/storymap` | マップ全体（ペルソナ・ジョブ・活動・手順・ストーリー・条件の件数・つながったイシューの進捗）と、つながりの抜け（`gaps`） |
| `GET/POST /projects/{key}/personas`、`PATCH/DELETE …/personas/{pkey}` | ペルソナ |
| `GET/POST /projects/{key}/jobs`、`PATCH/DELETE …/jobs/{jkey}` | ジョブ（活動とのつながりも） |
| `POST /projects/{key}/activities`、`PATCH/DELETE …/activities/{akey}` | 活動 |
| `POST …/activities/{akey}/steps`、`PATCH/DELETE /projects/{key}/steps/{skey}` | 手順 |
| `GET/POST /projects/{key}/stories`、`GET/PATCH/DELETE …/stories/{stkey}` | ストーリー（手順とのつながり・リリースも） |
| `POST …/stories/{stkey}/criteria`、`PATCH/DELETE /projects/{key}/criteria/{ackey}` | 受け入れ条件 |
| `PUT/DELETE …/stories/{stkey}/issues/{issueKey}` | ストーリーとイシューをつなぐ・外す |
| 並び替え | 各 `PATCH` の `position` |
| イシュー（既存） | `GET /issues/{key}` に `stories`（キー・タイトル・条件）を足す |

`gaps` で返す抜け: 手順につながっていないストーリー、ストーリーのない手順、条件のないストーリー、イシューのつながっていないストーリー、活動につながっていないジョブ。

MCP: `get_issue` の結果に `stories` を足す（B2-2）。読み取りの `get_storymap` を足す。書き込みのツールは M3（AI の下書き）で足す。

### 5.8 リリースのまとまり（リリーススライス）

オーナーの指定（2026-11-02）: 「リリースのまとまりは地図で示したい」。ユーザーストーリーマッピングでは、横に引いた線でリリースを区切り、いちばん上のまとまりを「まず動く最小の一通り」（ウォーキングスケルトン）にする。この線と、線ごとの**ねらい**を地図に出す。

- **まとまりそのものを持つ**: `req_releases`（マイグレーション 012）。名前・ねらい（goal: これで何ができるか）・状態（計画中 / 作っている / 出した）・目安（metric、任意）・並び。キーは `TAPP-RL1`（`R` は名前の「R1」とまぎれるので使わない）。
- **ストーリーは名前で指す**: `req_stories.release` は今のまま文字列。まとまりの名前を変えると、そのストーリーの `release` も一緒に変わる。ストーリーにまだないリリース名を書くと、その名前のまとまりが「計画中」でできる（まず書く で「R2 と書いて Enter」がそのまま動く。MCP も同じ）。
- **進み具合は計算する**: まとまりごとのストーリー数と、完了（つながったイシューがすべて完了）の数。状態は人（か AI）が決める。
- **地図での見え方**: 行の見出しに 名前・ねらい・状態・「n/m 完了」・目安。いちばん上の「出した」でないまとまりに **次に出す** を付け、その行の上に線を地図の端まで引く。出したものは薄く出す。見出しで名前・ねらい・状態を直せ、上下に動かせる。ストーリーのないまとまりは消せる（あるときは 409）。
- **まず書く / 整理して書く**: どちらも同じ。まず書く の「＋ リリース」の例は「いま / つぎ / あとで」。最初から作りはしない。
- **API**: `GET/POST /projects/{key}/releases`、`PATCH/DELETE /projects/{key}/releases/{rkey}`。`GET …/storymap` の `releases`（名前）は並びの順になり、`release_slices` に中身が入る。
- **AI**: `get_storymap` の `release_slices` を読み、ねらいのないまとまりには `update_release` でねらいを提案する（変える前に `ask_question`）。
- **入れていないもの**: スプリント（地図には載せない）。出したまとまりを畳む表示。まとまりへのドラッグ。

### 5.9 下書き（試してから、まとめて取り込む）

オーナーの指定（2026-11-03）: 「ストーリーマップはブレスト的にいろいろ試行錯誤して、その後決まるというプロセスがある。一時的な試行の場所で決めておいて、一気に入れたい」。4 つの案（下書き用のプロジェクト / マップの中の下書き / テキストで読み込む / 「仮」の印）から **案 1: 下書き用のプロジェクトから取り込む** を選んだ。

- **下書きはプロジェクト**: `projects.draft_of`（マイグレーション 013）が取り込み先を指す。キーは既定で `TAPPD1`, `TAPPD2` …（10 文字に収まるよう取り込み先のキーを縮める）。書き方の既定は「まず書く（quick）」。プロジェクト一覧・サイドバー・Jira 互換 API・MCP `list_projects` には出さない。取り込み先のマップのヘッダー「下書き」から作る・開く。
- **作り方は 2 つ**: いまのマップの**複製**（既定）か、**空**。複製は番号をそのまま使う（`TAPP-ST3` → `TAPPD1-ST3`）。連番も取り込み先の続きから始めるので、下書きで足したものの番号は取り込み先の番号とぶつからない。イシューとのつながりは複製しない。
- **対応表**: `req_draft_links` に、下書きの要素と取り込み先の要素の組と、そのときの中身のハッシュ（両側）を持つ。複製したときに書き、取り込むたびに、取り込みで書いた要素の分だけ書き直す（触っていない要素の基準は動かさないので、元で変えたことを、あいだに取り込みをはさんでも忘れない）。リリースのまとまりは、対応がなくても同じ名前なら同じものとみなす。
- **取り込みの予定**（`GET /projects/{draft}/import-plan`）: 3 者比較で決める。
  - 下書きで変えていない → 何もしない（取り込み先で変えたものはそのまま）
  - 下書きで変えた・取り込み先は変えていない → **変わる**（項目ごとに 前 → 後）
  - 両方で変えた → **変わる（衝突）**。上書きしてよいと明示しないと取り込めない（409）
  - 下書きで足した → **増える**（キーは取り込むときに付く。予定では「新規（TAPPD1-ST8）」と出す）
  - 下書きで消した → **消える**（アーカイブ。まとまりは、取り込み先にまだストーリーが残っていれば消さずに知らせる）
  - 取り込み先では消されたが、下書きで手を入れた → **戻す**（衝突として扱う）
  - 取り込み先にしかないもの（複製のあとに足したもの） → **そのまま残す**（一覧だけ出す）
  - 取り込み先が「整理して書く」のとき、手順のない新しいストーリーは「未整理に入る」と注意を出す。
- **取り込み**（`POST /projects/{draft}/import`、`{"force": true}` で衝突を上書き）: 1 つのトランザクションで、ペルソナ → 活動 → 手順 → ジョブ → リリース → ストーリー → 条件 の順に足して直し、消すものは逆の順に消す。予定はトランザクションの中で作り直す（見たあとに変わっていても、その時点の中身で判定する）。変更履歴には `from_draft` を付ける。まとまりの名前の入れ替え（R1 ⇔ R2）も通る。**人だけ**が取り込める（エージェントは 403）。
- **取り込んだあと**: 下書きは続けて使える。もう一度取り込むと、その後の違いだけが入る。いらなくなったら「下書きを捨てる」（プロジェクトのアーカイブ。取り込み先は変わらない）。
- **AI**: MCP `create_draft`（複製か空）と `get_import_plan`。下書きの中は今の道具（`create_story`・`update_story`・`update_release`）で直す。取り込みは画面でオーナーが行う。大きく考え直すときは下書きでやるよう、MCP の説明に書いた。
- **画面**: 取り込み先のマップのヘッダーに「下書き」（作る・一覧）。下書きのマップの上に帯（「TAPP に取り込む前の試し場所」・下書きを捨てる・TAPP に取り込む）。取り込みの予定は 増える / 変わる / 消える / 戻す に分けて出し、衝突には印を付け、「上書きして取り込む」に印を付けたときだけ取り込める。下書きのストーリー詳細ではイシューをつながない。
- **入れていないもの**: 2 つの下書きの間の比較。取り込みの取り消し（変更履歴は残る）。項目ごとに選んで取り込む。

### 5.10 MCP でマップそのものを作る

オーナーの指定（2026-11-04）: 「ペルソナと活動も MCP で入れられるようにしてほしい」。これまで MCP で書けたのはストーリーとリリースのまとまりだけで、ペルソナ・活動・手順は REST（トークンが要る）でしか入れられなかった。

- **足した道具**: `create_persona`・`update_persona`、`create_activity`（手順をまとめて渡せる）・`update_activity`、`create_step`・`update_step`。並び替えは `position`。活動のペルソナは `persona_key: ""` で外す。
- **`create_story` に足した項目**: `persona_key`・`i_want`・`so_that`（これまでは `update_story` でしか付けられなかった）。
- **消す道具は足していない**: 消すのは画面か、下書きで消してから取り込む（取り込み先ではアーカイブになる）。
- MCP の説明に、マップは `create_persona` と `create_activity` で組み立てる、と書いた。
