## 1. M1 で何が「固い」のか

| # | 固いところ | 使うときに起きること |
|---|---|---|
| K1 | キーが 6 系列（P・J・A・A-n・ST・AC） | 何を何と呼ぶかを覚えないと書けない |
| K2 | テーブル 11、そのうち 4 つが N:N の中間テーブル | API が 25 操作。AI も道具を覚える量が多い |
| K3 | 書く順番が決まった鎖: ペルソナ → ジョブ → 活動 → 手順 → ストーリー → 条件 → イシュー | マップに載せるには、先に活動と手順を作る必要がある |
| K4 | 受け入れ条件は前提・操作・結果の 3 欄 | 「こうなっていればいい」の 1 行が書きにくい |
| K5 | マップの軸が固定（横 = 手順、縦 = リリース） | 「朝」「AI」など、別の切り口で並べられない |
| K6 | 書く前に分類を決める（誰の・どの手順・どのリリース） | 思いついたときにすぐ書き留められない |

利用者はオーナーと AI だけ。重い分類は、共有する相手がいるときほどには役に立たない。

## 2. どの案でも守ること

**AI（MCP の `get_issue`）が、イシューの「なぜ」を読めること。** 08 §3 の B2-2 で見つけた抜けで、要求の層を足す一番の理由。以下の案はすべて、ここを満たす。

## 3. 三つの案

### 案 B「要求メモ」— いちばんゆるい

要求は **1 種類のメモ**（キー `TAPP-R12`）だけにする。本文は自由な Markdown。

- 本文の `- [ ]` の行が受け入れ条件になる（前提・操作・結果に分けなくてよい）。
- タグは任意。`@オーナー`（誰の）・`#朝`（場面）・`R1`（リリース）のように書く。ペルソナ・活動・リリースは**テーブルではなくタグ**になる。
- 親は任意（メモの下にメモ）。イシューにつなげられる。
- マップは保存しない。**タグで並べた見え方**にする（横 = `#` のタグ、縦 = `R` のタグ、など切り替えられる）。
- 色（未着手・実装中・完了）は M1 と同じく、つながったイシューから計算する。

```
req_notes      (id, project_id, num, title, body, parent_id NULL, position, created_at, updated_at, archived_at)
req_note_tags  (note_id, tag)              -- '@オーナー' '#朝' 'R1'
req_note_issues(note_id, issue_id)         -- N:N
（キーの連番と変更履歴は M1 の req_counters・req_changes を使う）
```

- なくなる固さ: K1〜K6 すべて。
- AI の「なぜ」: `get_issue` に、つながったメモのタイトル・本文・条件の行。
- PR #15 との関係: **置き換え**。009 の 11 テーブルとその API・画面を作り直す。本番にはまだ入れていないので本番データの移行はないが、M1 と同じくらいの作業になる。
- 弱いところ: 分類が人によってぶれる（タグの表記ゆれ）。抜け（手順はあるのにストーリーがない、など）を機械的に見つけにくい。

### 案 C「イシューで書く」— 新しいものをほとんど足さない

08 §5.2 で見送った案 B を見直したもの。要求は**イシューの新しい種別「要求」**にする。

- 受け入れ条件は今の受入基準（`acceptance_criteria`）を使う。
- 「なぜ」は親子で表す（作業のイシューの親が要求のイシュー）。
- マップは今のボードを、ラベルや親でグループにしたもの。
- 08 で見送った理由は「イシューが完了で閉じると要求も閉じてしまう」こと。これは「要求」の種別には**完了の状態を持たせない**ことで避ける。状態は子のイシューから計算して表示だけする。

```
issues.type に 'requirement' を足すだけ（マイグレーション 1 本）。新しいテーブルはなし
```

- なくなる固さ: K1・K2・K4・K6（K3・K5 は、親子とラベルの使い方しだい）。
- AI の「なぜ」: 今の `get_issue` で親を読めば足りる。新しい道具は要らない。
- PR #15 との関係: **置き換え**（009 は使わない）。
- 弱いところ: イシューの一覧・マイタスク・全体ボードに「要求」が混ざり、どこでも隠す設定が要る。受入基準は「今回の実装で確かめること」の意味もあるので、二つの意味が重なる。

### 案 D「M1 をゆるく使う」— おすすめ

**テーブルは M1 のまま**、決まりと画面をゆるめる。分類は書いた後に、必要になったら（AI に頼んで）付ける。

| # | 変えること | なくなる固さ |
|---|---|---|
| D1 | マップのいちばん上に**ひとこと入力**。何も選ばずにストーリーが入り、「未整理」の列に置かれる（今はマップの下にある「手順につながっていないストーリー」を、上の列に移す） | K3・K6 |
| D2 | ストーリーに**本文**（自由な Markdown）を足す。「したいこと」「そうすれば」の欄は、入っているときだけ出す | K6 |
| D3 | 受け入れ条件は**1 行**で書く（「結果」の欄だけ）。前提・操作は「詳しく」を押したときだけ出す。DB はもともと前提・操作が空でよい | K4 |
| D4 | ペルソナ・ジョブ・活動・手順は**使うときだけ**。活動が 0 件なら、マップは「リリース × 未整理」だけになる。パネルは閉じておき、「抜け」は警告の色をやめて数だけ出す | K3・K5（見た目） |
| D5 | **AI が整える**。AI がマップを読んで「ST7 を A1-2 に置いてよいか」「この条件はこう分けてよいか」を QA（yes/no）で聞く。オーナーは答えるだけ | K6 |

```
req_stories に body（本文）を 1 列足すだけ（マイグレーション 010）。ほかは画面と API の決まりの変更
MCP に update_story（本文・置き場所・条件）を足して、AI が整えられるようにする
```

- なくなる固さ: K3・K4・K6 は使う人から見えなくなる。K5 は使うまで出ない。K1・K2 は残るが、使う人は意識しなくてよい（キーは自動で付く）。
- AI の「なぜ」: M1 のまま（`get_issue` の `stories`）に本文が加わる。
- PR #15 との関係: **そのまま使う**。PR #15 をマージした後の小さな変更（D1〜D5）として進められる。
- 弱いところ: DB は固いまま。将来もっとゆるくしたくなったら（タグで並べるなど）、案 B の考えを足すことになる。

## 5. おすすめ

**案 D**。理由:

1. オーナーの指示どおり、M1 の画面をそのまま進められる。
2. 「固い」と感じるところ（書く順番・3 欄・先に分類）は、DB ではなく**書くときの決まり**から来ている。DB を変えなくてもゆるめられる。
3. 分類を AI に任せると、オーナーは書くことと答えることだけでよい。これは「利用者はオーナーと AI だけ」に合う。
4. 案 D を使ってみて、それでもタグで並べたい・ペルソナが要らない、とわかったら、そのときに案 B へ寄せればよい。案 D で書いた本文とタイトルは、案 B のメモにそのまま移せる。

## 6. 案 E: A と D をプロジェクトごとに選ぶ

オーナーの問い（2026-11-02）: 「案 D と案 A を両立できるか。画面は分かれてよい。プロジェクト単位で選べてもよい」。

**できる。** 案 D は M1 のテーブルに列を 1 つ（`req_stories.body`）足しただけで、ほかの違いは画面と「抜け」の見せ方だけだから。

- プロジェクトの設定 **要求の書き方** `requirements_mode`:
  - `quick` **まず書く**（案 D の画面）
  - `structured` **整理して書く**（案 A の画面）
- データは同じ。モードを切り替えても何も消えず、変わらない。API の決まり（何を受け付けるか）もモードで変えない。
- 新しいプロジェクトの既定は `quick`。マイグレーション 011 より前からあるプロジェクトは `structured`（M1 で作ったものの見え方を変えないため）。
- 画面からプロジェクトを作るときは、**要求の書き方を明示的に選ぶ**（何も選ばれていない状態から始め、選ぶまで「作成」を押せない）。既定の `quick` は、API で指定しなかったときだけ使う。

| | まず書く（quick） | 整理して書く（structured） |
|---|---|---|
| 書き始め | マップの上のひとこと入力 → 未整理の列 | 手順 × リリースのマスの ＋ |
| 手順のないストーリー | 最初の列「未整理」 | マップの上に「⚠ 未整理 N件」（抜けとして） |
| 本文 | いつも出る | 書いてあるときだけ出る（切り替えても消えない） |
| したいこと・そうすれば | 「項目を足す」で | いつも出る |
| 受け入れ条件 | 1 行。前提・操作は「詳しく」 | いつも前提・操作・結果の 3 欄（1 行のものは前提・操作が「—」） |
| ペルソナ | 使うときだけ | いつも出る |
| 抜け | 数だけ | 警告の色 |
| AI（MCP） | `get_storymap` の `mode` が `quick`。1 行でよい | `mode` が `structured`。手順の下に置き、3 欄を埋め、抜けを直すものとして扱う |

マップのヘッダーに今のモード（「まず書く」「整理して書く」）を出し、押すとプロジェクト設定へ移る。

使い分けの例: ひとりで思いつきを溜めるプロジェクトは「まず書く」。ペルソナや手順が固まって、抜けなく作りたいプロジェクトは「整理して書く」。ひとつのプロジェクトで、始めは「まず書く」、整ったら「整理して書く」に切り替えてもよい。

実装はブランチ `exp/req-e`（`task-app-next/e-both`、案 D の上）。確認事項は [extra-15](checkpoints/extra-15.md)。
